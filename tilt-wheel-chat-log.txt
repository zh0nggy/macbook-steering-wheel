ASSISTANT:
[searched the web for Apple Silicon IMU access and Assetto Corsa on Mac]

Good news and one real blocker.

The gyroscope is there. Apple Silicon MacBooks (M2-M5 confirmed by community
reverse-engineering) carry an undocumented MEMS IMU -- 3-axis accelerometer AND
3-axis gyro -- managed by the Sensor Processing Unit, readable at roughly 800Hz
through IOKit HID callbacks. Apple exposes it through no public API, so you'd
lean on existing work like olvvier/apple-silicon-accelerometer or the macimu
Python package. Intel MacBooks only ever had the Sudden Motion Sensor, which is
accelerometer-only with no gyro.

The blocker is the opposite end of the pipe. Reading tilt is solved; presenting
yourself to the game as a steering wheel is not. On Windows that's a one-
afternoon problem -- vJoy or ViGEmBus give you a virtual joystick in user space.
macOS has no equivalent. Creating a virtual HID device requires a DriverKit
system extension with an entitlement you request from Apple, which is why
Karabiner-Elements ships an actual signed driver just to fake a keyboard.
Sending synthetic key events with CGEvent is the easy fallback, but it gives you
digital left/right rather than analog steering angle, which defeats the point.

Second constraint: Assetto Corsa has no Mac build. It runs through CrossOver
(Whisky is archived and unmaintained as of 2026) or Windows-on-ARM in Parallels.

The four layers you'd need to build:
  1. Sensor read - small Swift or Python daemon over IOKit HID
  2. Motion-to-steering - the actually interesting engineering. Integrating raw
     gyro angular velocity drifts within seconds. You need the accelerometer's
     gravity vector for absolute roll, fused with gyro for responsiveness --
     a complementary filter, or Madgwick if you want to be thorough.
  3. Virtual controller - the problem layer
  4. Telemetry and the coach - AC's shared memory (acpmf_physics,
     acpmf_graphics, acpmf_static) or UDP remote telemetry

The part your plan is missing: "recommended speed and gear for the track" has no
source of truth in your design. You can't derive it from telemetry alone -- the
game doesn't tell you the optimal line. Either compute it physically from track
curvature and grip limits (hard), or record reference laps and build a lookup
from track position to speed and gear (tractable, and an honest "ML" line on a
resume). Take the second.

Also deliver the coaching as speech rather than an on-screen overlay -- you
cannot read text while steering a laptop.

Budget note: analog steering feels broken past roughly 20ms of input latency.

One correction to what I told you earlier. I'd said vJoy. Don't start there. The
original vJoy branch runs into Windows 11 driver-signature enforcement, and the
workarounds are either disabling signature enforcement -- a genuinely bad idea
on your daily-driver machine -- or pulling community forks from third-party
mirrors. For a kernel-mode driver, unverified mirrors are a real risk.

Use ViGEmBus instead, from Nefarius's official releases only. Properly signed,
installs on Windows 11 without touching Secure Boot, presents a fully compliant
virtual Xbox 360 pad. Python binding is vgamepad. Nefarius has published an
end-of-life statement, so it's maintained-in-place rather than actively
developed.

Tradeoff: AC sees an Xbox pad and applies its gamepad input filters, including
speed-sensitive steering, which will fight your own response curve. Turn those
down in Content Manager before you conclude your filter is broken.

Two decisions to make now: pick one car and one track and freeze them. And since
none of you sim-race, you have no fast laps to build a reference model from, so
the coach targets your own personal-best pace rather than optimal pace.

ASSISTANT:
Two days for steering-only is realistic, and it removes the biggest risk.

You don't need the gyro for the MVP. The accelerometer's gravity vector alone
gives you absolute roll angle, with no drift and no integration. Tilt the

not a dependency. So the "does the M4 Air have a gyro" question stops being a
gate and becomes a day-3 upgrade.

macimu's docs say usage 3 is the accelerometer and usage 9 the gyroscope on the
same physical IMU behind AppleSPUHIDDriver, believed to be a Bosch BMI286.

ASSISTANT:
The USB-C part is a misconception, and it's the important one.

A Mac cannot present itself as a controller over USB-C. Laptops are USB HOSTS,
not USB DEVICES -- the port can drive a mouse, but it can't pretend to be one.
There's no macOS setting or cable that changes this.

What makes Windows see a controller is ViGEmBus, a driver running ON THE WINDOWS
PC, which creates a fake controller that exists purely in software. The game
sees that fake controller and has no idea a Mac is involved. The Mac's only job
is to shout numbers at the PC over the network.

The "connection" is a network connection, not a controller connection. Same WiFi
is all you need.

File table given. Key point: two programs run at the same time, one on each
machine. mac_sender.py on the Mac and pad_receiver.py on Windows, both open,
both left running. Neither works alone.

Your USB-C instinct isn't wrong, it's just the wrong device -- the ESP32 is
exactly the thing that CAN be a real USB gamepad (S2/S3 have native USB device
support). Day-3 upgrade, not the MVP.

File-by-file explanation:

                   sides agree on. Copy to both machines unchanged.
  imu_probe.py   - throwaway diagnostic. Tells you which sensor axis is which.
  mac_sender.py  - real Mac program. Read sensor, compute tilt, send number.
  pad_receiver.py- real Windows program. Receive number, move fake controller.
  mock_sender.py - fakes the Mac so you can test the Windows half alone.

On gears and brakes: neither keyboard works well.

The Windows keyboard needs zero code, but your hands are wrapped around a laptop
you're rolling side to side, so you can't reach it. Only works if a teammate
presses keys -- a party trick, not a product.

The Mac keyboard is where your hands already are, but Mac keypresses do not
reach Windows. You'd have to capture keys on the Mac with pynput, put their
state in the UDP packet, and map them to gamepad buttons in the receiver. Needs
macOS Accessibility permission.

For the two-day MVP: NEITHER. Turn on AC's automatic gearbox and send a constant
throttle from the Mac. Steering is the only thing you control. Complete, honest
demo, and it keeps two days as two days.

One trap for later: steering is a STATE -- sending "0.42" a hundred times a
second is fine. A gear shift is an EVENT. If you send gear_up=true at 100Hz
while holding the key for a fifth of a second, the game sees twenty upshifts.
Fix: send a shift COUNTER that only increases, and have the receiver pulse the
button once when the number changes.
